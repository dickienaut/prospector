# §4d mandate-diff on cadence + the §9c frozen-prior invariant (M5 step 3, part 2)

*Decision record, 2026-07-06. Implements spec §4d (mandate) + the §9c frozen-prior invariant (SUBTLE
BIT #2), following §9d. §9e (dispersion shadow clock) is the step-3 remainder.*

## The determination (why this was built now, not deferred)

The design thread's rule for §9c: wire it **only if doing so wires the mandate live path** (submissions
→ detect a new prospectus → fetch → freeze → diff against the frozen prior), so the invariant governs
real execution — otherwise defer, because a CONTRACT guarding an unbuilt path is the exact anti-pattern
Science flagged. **Checked the §4d slot state: the mandate path is fully built.**
- `ingest/prospectus.py` `ProspectusIngest.pull` is a real fetch+freeze (via `EdgarClient.filing_text`),
  not a stub; `diff_mandate` / `extract_mandate` / `html_to_text` are built and tested.
- `sensors/mandate.py` `scan` orchestrates freeze-current → diff-strategy-section-vs-frozen-prior →
  route (`mandate.changed` onto live leads / `_system`, or a `fault` on unreliable extraction). It
  already takes `prior_accession` as an explicit param, documented as the frozen prior (§9c-honoring).
- `edgar.latest_prospectus` gives the current; the config `mandate:` block carries the reader knobs.

So wiring the runner mandate pass **runs real execution** — a baseline on first sight, a diff once a
fund files a new prospectus across cadences — and it is **self-sufficient** (records on `_system` even
with no live lead). Not a CONTRACT guarding the unbuilt → **do it.**

## What was built

`runner._run_mandate` (wired at the §4d SLOT in `_run_sensors`): for each registered (watched) fund —
`fund_registry.all_funds()` — fetch submissions, take `latest_prospectus` as the current, and the
**last FROZEN prospectus** as the prior via `_last_frozen_prospectus`, then `mandate.scan`. Plus
`edgar.prospectus_history` (all prospectus-family filings, newest-first) for the frozen-prior walk, and
a shared `_lead_context` helper (universe tickers → series_ids + active lead ids) refactored out of the
§9d `_active_lead_sectors` and reused for the mandate routing.

## The §9c invariant, and how the test proves it

`_last_frozen_prospectus` walks `prospectus_history` newest-first and returns the most-recent accession
that isn't the current one AND that we hold **frozen** (`prospectus.has_frozen`) — sourced from the blob
store, **never** the registry `prospectus_accession` field. Why it matters: an identity pass earlier in
the same run may have advanced that field to the new filing, so reading the prior from it would diff the
new filing **against itself** and miss a real mandate change.

The gate test (`test_mandate_diff_uses_the_frozen_prior_not_the_advanced_registry_field`) seeds exactly
that hazard — registry field already `== B` (the new accession), the true prior `A` held only as a
frozen blob, submissions' latest `== B`, `filing_text(B)` a substantive rewrite — and proves the diff
fires against the frozen `A`: a single `mandate.changed` with `prior_accession == A`. Had the runner
read the field, it would have diffed `B` vs `B` → no change → no event. Prove-the-invariant, the §9c
analog of §9d's fires-not-called. Plus: baseline on first sight (freeze, no event) and a per-fund fetch
failure as a soft fault.

## Notes / bounds

- **Silent (§10):** `mandate.changed` never pushes; the human adjudicates cosmetic-vs-substantive.
  Extraction-unreliable → `fault` (flag, never a false change).
- **Watched set = all registered funds.** A submissions fetch per registered fund per tick; bounded
  (the sector ETFs + launched funds). No weekly gate (cadence-agnostic runner; M7 scheduling throttles).
- **Rebalance (the §4d holdings-diff sibling) stays a SLOT** — it needs holdings ingest, a separate
  vertical. No CONTRACT touched (no schema change; `FundEntry` untouched).
