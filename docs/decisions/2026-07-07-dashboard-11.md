# §11 read-only Streamlit dashboard — the surface that watches the evidence accumulate

*Decision record, 2026-07-07. Implements spec §11 / rev13 §8b (the read-only dashboard). Slice 3 of the
spawner arc (sector-prices → xcorr-live → **dashboard**). With this, the "runner earns its keep" pair —
a proven live spawner + a surface to watch it — is both landed.*

## Shape: tested view-models + a thin render shell

The dashboard was greenfield (no scaffold; Streamlit not a dependency). Built in two layers so the
load-bearing part is tested and the UI stays thin:
- **`dashboard/views.py` — pure view-models.** Every panel's data-shaping is a pure function over the
  fossil record (folds of events / run-log rows). NO streamlit import, NO writes, NO recompute or fetch.
  This is where the logic lives, and it is fully unit-tested (12 tests) without a browser.
- **`dashboard/app.py` — the thin `st.*` shell.** Renders the view-models; no logic of its own.

**Streamlit is an OPTIONAL extra** (`[project.optional-dependencies] dashboard`), so the core (runner,
sensors, the test suite) stays lean and offline — `views.py` never imports streamlit, and the shell is
only loaded under `uv sync --extra dashboard`. Launch:
`PROSPECTOR_STORE=./store streamlit run prospector/dashboard/app.py`.

## Layout: lead with the three, everything else a click deeper

The §11 panel *set* is fixed by the spec; the real latitude is at-a-glance priority — a UX call. The
dashboard's purpose is **watching the evidence accumulate**, so the top of the page leads with the three
things that serve that, and the rest is collapsed behind expanders (a click deeper):
1. **Active leads** — the live (non-shadow) xcorr firings, ranked recency × |z|. The real evidence.
2. **Coverage / dormant pile** — the §10 blindness map (where intake can't yet resolve a launch), ranked
   by disposition, latest-per-fund. Where we're blind.
3. **Health** — the weekly dead-man + last-run up top (metrics), the fault log below. Is it running /
   what broke.

A click deeper (collapsed): dispersion shadow/burn-in, launch survey, macro catalog, manual-resolution
queue, run history, registry-health + unknown-type panel, per-lead thaw-backward timeline.

## CONTRACT honored (spec §11 / CLAUDE.md)

- **Read-only, no recompute on view, no autorefresh, no run-now.** The shell only renders folds the
  runner already wrote; there is no refresh timer and no button that runs anything. The discipline
  variable is computation cadence, not display richness (the deliberate inversion of an autorefreshing
  cockpit — a surface that only renders stored runs cannot reward compulsive checking).
- **The dispersion shadow panel renders honestly-empty** ("dispersion: not yet wired (§4b needs the
  holdings/constituent-price vertical)") — never a faked record, the same flag-the-blind-spot discipline
  as the dormant pile.
- **The macro catalog is inert context** — `off-thesis-real` verdicts for human consultation only; never
  a trade/tilt trigger, never an alert stream / "regime forming" push (CLAUDE.md).
- **The launch panel is survey-only, never pushed.**
- **Firewall:** the dashboard reads only this store's own record — never the portfolio config or a trade
  path (guarded by the source grep, like the runner).
- **Readiness surfaced, never auto-promoted:** the shadow burn-in clock shows days-elapsed vs
  `shadow_days`, but promotion stays a human config flip (§9e CONTRACT).

## What renders where (the fold-state shapes)

Panels read the folded lead state (`fold()`), the run-log `runs` table, and `_system` event streams:
- active leads / macro catalog / shadow / registry-health / unknown-types ← `fold_all_leads` +
  `active_nonshadow` (the same §8a/paging oracle filter), reading `status`/`shadow`/`spawner`/`verdict`/
  `latest_z`/`spawned_at`/`unknown_types`;
- ceiling tripwire ← `len(active_nonshadow)` vs `oracle.active_lead_ceiling`;
- launch survey ← `launch.unverified` events; dormant pile ← latest `launch` corroboration per series_id
  on `_system`, grouped by disposition (a `match` never appears — it accretes onto a live lead);
- fault log ← `fault` events; heartbeat ← `recent_runs` vs a 7-day floor; manual queue ← the
  ResolutionMachine's `manual_queue`; per-lead timeline ← `events_for_lead` in (ts, event_id) order.
