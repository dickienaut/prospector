## Gates closed

**Item 10 — "`deploy.sh` refuses under a held lock" → ✅ PASS (and it found a bug).** Untestable until the
single-writer lock shipped in v1.0.3. Tested deterministically by nesting the deploy inside a held lock
(`pros store lock-run -- ops/deploy.sh v1.0.4`), so the inner acquire hits real contention — no background
race. **Result: refused, and prod stayed at `v1.0.3` — nothing swapped under an in-flight tick.**

But it printed the *wrong cause*: `ERROR: deploy mutation (checkout / uv sync) failed under the lock`
instead of `STOP: a scheduled tick is in flight — retry in a few minutes`. Root cause: `rc=$?` sat
immediately after `if ! ( … ); then`, which captures the **negation's** status (always 0), never the inner
`lock-run`'s **75** — so the 75 branch was unreachable dead code. Filed as **DEPLOY-LOCK-MSG**
(`docs/bugs/INDEX.md`), fixed in the same change (`|| rc=$?`, which is also errexit-safe), and verified
**RED→GREEN** by re-running the contention test: correct STOP message, prod unmoved both times.

*The gate earned its keep exactly the way a gate should — it passed on **behaviour** and failed on
**diagnosis**, which is only discoverable by actually running it.*

**Item 11 — dual `lock-path` identity → ✅ re-verified.** Both checkouts resolve
`/Users/lyledickie/prospector/store/run.lock`, so the deploy-side lock is real, not decorative
