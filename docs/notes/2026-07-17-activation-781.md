## The finding + the remediation (the real work of the day)

- **Prod was `v1.0.2`, 139 commits behind `main`; the M7 safety tail was not in production:**
  - single-writer lock (M7-04/06) — `pros store lock-path`/`lock-run` **did not exist** in prod;
  - heartbeat cadence **catch-up** (M7-01) — v1.0.2 uses the fragile local-Sunday gate that **silently drops** a slept-through heartbeat (0 `heartbeat_is_due` refs vs 3 on main);
  - backup-health-in-heartbeat (M7-02); BK-1 / BK-2 backup fixes.
  - *These are precisely the commits that make **unattended** operation safe — a precondition of removing the human from the loop, not "getting current."*
- **DEPLOY-OVERLAY-DRIFT was live** — dev had **no** overlay, so `deploy.sh` (run from dev) resolved `store.root` to `store/run.lock` (dev's own store), not prod's. The deploy-side lock has been **decorative since it shipped**; the dual-`lock-path` rider caught it before a deploy relied on it.
- **Remediated (2026-07-17):**
  1. Mirrored prod's overlay onto dev → `lock-path` from dev now resolves to prod's store (single check; item 11's dual check came after the deploy).
  2. Unloaded the LaunchAgent — the first deploy of the lock **cannot be protected by the lock**, so the collision was removed by hand, once.
  3. Cut `v1.0.3` at `d714d82`; `ops/deploy.sh v1.0.3` (uv sync clean).
  4. Reloaded the scheduler (18:30 daily). Item 11 PASS; prod now holds the lock.

- **Stale `Operation not permitted` error** — referenced the old `~/Documents/coding/prospector` path; resolved
  by the Jul-12 plist reinstall (`err.log` untouched since Jul 12 19:46). Documented so it is never
  re-investigated.
- **`push` + `heartbeat` double-send — new finding, first observed tonight; a Design call, not fixed here.**
  When a run is both page-worthy (`pushed=True`) *and* the heartbeat is due, the runner calls
  `notifier.push(ctx)` **and** `notifier.heartbeat(ctx)` (runner.py ~417–430) — **two near-identical emails**
  from the same context (subjects differ; bodies match). Not a correctness bug — both sends are intended — but
  a nuisance that **recurs on every deploy's first run** (the `config.changed` push coincides with the first
  heartbeat, as it did tonight). Worth a decision: coalesce a coincident push+heartbeat into one send (the push
  already carries the `Heartbeat: OK` line), or differentiate them so they don't read as accidental dupes.
